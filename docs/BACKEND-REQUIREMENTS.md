## 1. 定位：这份需求要证明什么

### 1.1 要证明的（每一条都能落到代码与答辩话术）

| 能力维度 | 在本项目中的落地 |
| --- | --- |
| **分层架构** | Controller / Service / Mapper 三层职责分离，Controller 内**零业务逻辑** |
| **RESTful API 设计** | 统一资源路径、HTTP 方法语义、状态码、响应体结构 |
| **鉴权与授权** | Spring Security + JWT 双 token（access / refresh）；ADMIN / EDITOR 两级角色 |
| **事务一致性** | 文章「发布」跨 3 张表写入，`@Transactional` 保证原子性与回滚 |
| **并发控制** | 版本号乐观锁，并发编辑冲突返回 `409` 并提示合并 |
| **缓存** | Redis 缓存文章详情与热门列表，写时失效（`@Cacheable` / `@CacheEvict`） |
| **数据建模** | 12 张表，含**多对多**、**历史版本**、**审计日志**、**逻辑删除** |
| **工程规范** | 统一响应体、全局异常、参数校验、Swagger、Flyway、AOP 日志、测试、Docker、CI |
| **接口契约思维** | 后端契约贴合既有前端调用，前端仅改数据访问层（见 §7） |

### 1.2 明确**不**证明的（本阶段不做，避免范围失控）

微服务与注册中心 · 消息队列 · 分库分表 · 分布式锁 · 多租户 · 细粒度按钮级权限 · 全量单元测试覆盖 · 灰度发布 · Prometheus/Grafana 监控体系

## 2. 范围边界

### 2.1 保留不变（前端已完成，后端照原样实现）

| 区域 | 内容 |
| --- | --- |
| 展示站点 | 首页 / 博客列表 / 阅读页 / 项目 / 关于 / 页内切换 / 移动端导航 |
| 后台模块 | 仪表盘 · 文章管理 · 项目管理 · 媒体库 · 站点配置 · 设置 |
| 交互体验 | 搜索、排序、分页、批量删除、Markdown 预览、图片插入、主题切换 |

> **搜索/排序/分页的用户体验不变**，但**实现位置从「浏览器内存」下沉到「服务端 SQL」**——这是后端改造的必然结果，也是加分项。

### 2.2 新增（纯粹为了体现后端能力）

| # | 功能 | 为什么加它 |
| --- | --- | --- |
| 1 | **文章状态机**：草稿 / 已发布 / 已归档 | 非法流转校验 + 与角色联动，是最典型的「业务逻辑」而非 CRUD |
| 2 | **文章历史版本**：每次发布留存快照，可查看与回滚 | 让「事务」有真实内容；回滚又是一次跨表事务 |
| 3 | **操作审计日志**：谁、何时、对什么、做了什么 | AOP + 自定义注解，常规工程实践，答辩可直接演示 |
| 4 | **两级角色**：ADMIN（全部）/ EDITOR（仅内容） | 授权建模能力，成本极低（两张小表） |
| 5 | **回收站**：逻辑删除 + 恢复 + 彻底删除 | 体现数据安全考量，也是「逻辑删除」这一常规模式 |
| 6 | **置顶与排序**：`is_top` + `sort` | 原 S2.1 未做；纯字段设计，成本低，且影响力排序是常见需求 |
| 7 | **登录风控**：连续失败锁定 + 登录日志 | Redis 计数器的真实用途（而非为缓存而缓存） |
| 8 | **浏览量统计**（可选） | 演示「Redis 自增 + 定时落库」，性价比高 |

### 2.3 明确不做

草稿多人协作 · 评论 / 点赞 / 关注 · 多语言 · 中文分词全文检索（先用 `LIKE`，留接口） · 数据看板图表 · 图片自动压缩与水印 · 邮件通知

### 2.4 「最小但完备」的判定标准

本项目只在「**最小**」与「**完备**」之间取一个点。判定标准三条：

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | **每个常规环节至少出现一次** | 不要求做全做深，但常规后端该有的环节一个都不能缺 |
| 2 | **能删到「再删就讲不完整」为止** | 任何模块被删，都会让某个环节在答辩时「无话可说」，则保留 |
| 3 | **技术必须解决真实问题** | 判定标准不是「有没有引入这个技术」，而是「这个技术有没有解决本项目的一个真实问题」 |

#### 2.4.1 必须有的（缺一即不成立）

| 常规后端环节 | 本项目的最小落地 | 判定 |
| --- | --- | --- |
| 分层架构 | Controller / Service / Mapper 三层，职责写入纪律清单 | 必备 |
| 统一响应与异常 | `Result` + `ErrorCode` 枚举 + `@RestControllerAdvice` | 必备 |
| 参数校验 | `@Valid` + JSR-303 注解，错误由全局异常统一转换 | 必备 |
| 认证 | 账号密码登录 → JWT | 必备 |
| 授权 | 2 个角色 + `@PreAuthorize` | 必备 |
| 数据库建模 | 12 张表，含 1 个多对多、1 个历史版本表 | 必备 |
| 数据库版本管理 | Flyway 脚本随代码走 | 必备 |
| CRUD | 文章 / 项目 / 媒体 | 必备 |
| 分页查询 | MyBatis-Plus 分页插件，查询下沉到 SQL | 必备 |
| 事务 | 文章发布跨 3 张表写入 | 必备 |
| 并发控制 | 版本号乐观锁 → `409` | 必备 |
| 缓存 | Redis + Spring Cache 注解，写时失效 | 必备 |
| 日志 | 请求日志（含耗时）+ AOP 审计日志 | 必备 |
| 接口文档 | springdoc-openapi | 必备 |
| 文件上传 | 本地存储 + `StorageService` 接口抽象 | 必备 |
| 测试 | 3～5 个核心用例（状态机 / 乐观锁 / 鉴权） | 必备（最低限度） |
| 容器化 | Docker Compose 一键起 app + mysql + redis | 必备 |
| CI | 一条流水线：编译 + 测试 | 必备 |

#### 2.4.2 不做也不影响完备性的

| 环节 | 为什么可以不做 |
| --- | --- |
| 消息队列 | 本项目没有异步解耦场景，硬加会被追问「为什么需要 MQ」 |
| 分布式锁 / 分布式缓存 | 单机部署，不存在跨节点竞争 |
| 微服务 / 注册中心 / 网关 | 单人项目，会**稀释**核心能力展示 |
| Prometheus / Grafana 监控体系 | 属运维体系，不是后端开发能力 |
| 全量测试覆盖 | 覆盖核心分支即可，不追求覆盖率数字 |
| 灰度 / 蓝绿发布 | 没有真实流量，做了也无从验证 |

#### 2.4.3 「假完备」反例（务必避免）

引用了技术但没有解决真实问题，**等于没做**：

| 反例 | 为什么算没做到 |
| --- | --- |
| Service 层只有一行 `mapper.selectById()` | 等于没分层，只是多套了一层壳 |
| 加了 `@Transactional` 却没有任何跨表写 | 等于没事务 |
| 依赖里引了 Redis 但业务代码没用上 | 等于没缓存 |
| 建了角色表但只有 1 个角色、从不判权限 | 等于没授权 |
| 写了 Flyway 脚本但表仍是手工建的 | 等于没版本管理 |

> **一句话**：完备性看的是「**有没有解决真实问题**」，不是「依赖列表有多长」。

## 3. 功能需求

**变更标记**：🔁 保留（功能不变、实现重写） · 🆕 新增 · 🔧 改造（行为微调）
**优先级**：P0 必须 · P1 应做 · P2 可选

### 3.1 认证与账号（FR-B-A）

| 编号 | 需求 | 优先级 | 变更 |
| --- | --- | --- | --- |
| FR-B-A01 | 用户名 + 密码登录，签发 access token（短效）与 refresh token（长效） | P0 | 🔁 |
| FR-B-A02 | 凭据错误统一返回「用户名或密码错误」，**不区分账号是否存在** | P0 | 🔁 |
| FR-B-A03 | access token 过期后可用 refresh token 静默换取新 token | P0 | 🆕 |
| FR-B-A04 | 登出：服务端将 token 加入黑名单（Redis），立即失效 | P0 | 🔧 |
| FR-B-A05 | 修改密码需校验旧密码；成功后**吊销该用户全部 token** | P0 | 🔁 |
| FR-B-A06 | 连续登录失败 5 次锁定账号 15 分钟 | P1 | 🆕 |
| FR-B-A07 | 记录登录日志（时间、IP、UA、结果） | P1 | 🆕 |
| FR-B-A08 | 角色模型：ADMIN 可管理账号与配置，EDITOR 仅可管理内容 | P1 | 🆕 |

| 编号 | 需求 | 优先级 | 变更 |
| --- | --- | --- | --- |

| FR-B-P05 | 参数校验：标题必填且 ≤ 100 字、正文 ≥ 6 字、日期格式 `yyyy-MM-dd` | P0 | 🔁 |

## 4. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 列表接口（1 万篇文章）响应 < 200ms；输入即搜接口做 300ms 防抖 + 分页限制 |
| 安全 | 密码用 BCrypt 存储；接口全部鉴权（除登录与展示站点读接口）；SQL 由 MyBatis 参数绑定防注入；上传文件校验 MIME 与后缀 |
| 并发 | 文章编辑使用乐观锁；批量操作在单个事务内完成 |
| 一致性 | 逻辑删除统一由 MyBatis-Plus 拦截，业务代码不手写 `deleted = 0` |
| 可维护 | 配置分环境（dev / prod）；数据库变更由 Flyway 管理，禁止手工改表 |
| 可观测 | 请求日志（含耗时与 TraceId）；审计日志留痕；接口文档自动生成 |
| 兼容 | 接口返回结构贴合既有前端契约，前端仅改数据访问层 |

## 6. 验收标准

1. **接口闭环**：前端所有数据操作都经由自研 API，仓库内**不存在任何 Supabase 客户端调用**；
2. **分层清晰**：Controller 内无业务判断与 SQL；Service 内无 `HttpServletRequest`；
3. **事务生效**：发布流程中任一表写入失败，`post` / `post_revision` / `operation_log` 全部回滚（可用断点或异常注入验证）；
4. **乐观锁生效**：用两个会话同时提交同一篇文章，第二次返回 `409` 且内容未被覆盖；
5. **缓存生效**：连续两次请求文章详情，第二次命中缓存（日志可见）；编辑后缓存被清除；
6. **鉴权生效**：无 token 访问 `/api/posts` 返回 `401`；EDITOR 角色访问账号管理返回 `403`；
7. **逻辑删除生效**：删除后列表不可见，回收站可见，可恢复；数据库 `deleted = 1`；
8. **工程规范**：Swagger 可打开且接口齐全；`mvn test` 通过；Docker Compose 一条命令起全栈；CI 绿；
9. **前端可用**：改造后前端功能与改造前**行为一致**（走一遍原有回归清单）。

## 8. 功能变动大吗（直接结论）

**不大。可以概括为「三个不变 + 三个新增」。**

| 结论 | 说明 |
| --- | --- |
| **不变 1**：功能范围 | 现有 6 大模块、全部页面与交互 100% 保留，一条需求都没砍 |
| **不变 2**：数据字段 | 文章/项目/配置的核心字段完全沿用，前端类型定义基本不动 |
| **不变 3**：页面结构 | 22 个 UI 组件零改动，不需要新增页面、不需要重做设计 |
