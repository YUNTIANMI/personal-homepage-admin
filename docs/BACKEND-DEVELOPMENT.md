## 2. 各阶段详述

### 阶段一 · 地基（工程骨架与数据模型）

**目标**：把工程规范与数据结构一次性定死，让后续每个阶段都只在既有框架内填内容。

**覆盖需求**：无直接 FR，为全部 38 条需求提供底座。

**使用技术**

| 技术 | 用来做什么 |
| --- | --- |
| Spring Boot 3.x + Maven | 工程骨架、依赖管理 |
| MyBatis-Plus | 分页插件、乐观锁插件、`MetaObjectHandler` **此阶段就配好**（后续各阶段直接复用，避免逐表处理） |
| Flyway | 12 张表的版本化建表 |
| MySQL 8 / Redis 7 | 用 Docker Compose 起本地环境 |
| springdoc-openapi | 接口文档 |
| Lombok | 简化实体样板代码 |

**关键产出**

- 分层包结构：`common` / `config` / `controller` / `service` / `mapper` / `entity` / `dto` / `vo`（见架构文档 §3）
- `common/`：`Result`、`PageResult`、`ErrorCode`、`BizException`、`GlobalExceptionHandler`
- `MybatisPlusConfig`：分页插件 + 乐观锁插件 + 字段自动填充
- `application-dev.yml` / `application-prod.yml`（敏感项走环境变量）
- `docker-compose.yml`（mysql + redis）
- Flyway `V1__init_schema.sql`（**12 张表 + 全部索引**）、`V2__seed_data.sql`（2 个角色 + 1 个 ADMIN + 1 行站点配置）
- `GET /api/ping` 用于验证全链路

**完成标准**

1. `docker compose up -d` → 启动应用 → `/swagger-ui.html` 可打开；
2. `GET /api/ping` 返回 `{ code: 0, message: "成功", data: "pong" }`；
3. `SHOW TABLES` 能看到 12 张表，索引齐备。

**注意**

- **本阶段的规范后续不允许再改**（统一返回格式、异常处理、分层职责），否则全量返工；
- 三个 MyBatis-Plus 插件务必此时配好，「乐观锁」到阶段四才用得上，但配置属于地基。

### 阶段二 · 身份（认证与授权）

**目标**：完成登录闭环与权限模型，此后所有接口**默认受保护**。

**覆盖需求**：`FR-B-A01` ～ `FR-B-A08`

**使用技术**

| 技术 | 满足的需求 |
| --- | --- |
| Spring Security 6 过滤链 | 全局鉴权入口（`FR-B-A01`） |
| jjwt：access（30 min）+ refresh（7 d） | 无状态登录与静默续期（`FR-B-A01`、`A03`） |
| `PasswordEncoder`（BCrypt） | 密码加密存储（`FR-B-A01`） |
| Redis 黑名单（按 `jti`） | 登出立即失效（`FR-B-A04`） |
| `sys_user.token_version` 自增 | 改密后吊销全部旧 token（`FR-B-A05`） |
| Redis 计数 + `locked_until` | 登录失败锁定（`FR-B-A06`） |
| `login_log` 表 | 登录日志（`FR-B-A07`） |
| `sys_role` / `sys_user_role` + `@PreAuthorize` | 两级角色授权（`FR-B-A08`） |

**关键产出**

- `JwtTokenProvider`：签发 / 解析 / 校验
- `JwtAuthenticationFilter`：解析签名与过期 → 查黑名单 → 塞入 `SecurityContext`
- `SecurityConfig`：放行 `/api/auth/login`、`/api/auth/refresh`、`/api/ping`
- `/api/auth/login`、`/api/auth/refresh`、`/api/auth/logout`、`/api/auth/me`、`/api/auth/password`
- `LoginUser` + `SecurityUtils`（统一取当前用户）

**完成标准**

1. 连续 5 次错误密码 → 第 6 次返回 `423 ACCOUNT_LOCKED`；
2. 无 token 访问受保护接口 → `401`；
3. 登出后立刻用原 token 访问 → `401`（黑名单生效）；
4. 用一个临时测试接口验证：ADMIN 通过、EDITOR 返回 `403`；
5. `login_log` 中成功与失败记录都有。

**注意**

- Spring Security 过滤链是新手**最容易卡住**的地方：先用最简配置跑通「能放行 + 能拦截」，再逐步收紧；
- access 有效期别设太长，否则「黑名单吊销」就失去意义。

### 阶段三 · 内容（CRUD + 分页下沉 + 前端接通）

**目标**：主业务读写闭环，并**首次把前端跑在自研后端上**——这是第一个可完整演示的版本。

**覆盖需求**：`FR-B-P01`～`P05`、`P10`｜`FR-B-J01`～`J05`｜`FR-B-U01`～`U03`｜`FR-B-S01`～`S02`｜`FR-B-T06`

**使用技术**

| 技术 | 满足的需求 |
| --- | --- |
| MyBatis-Plus `BaseMapper` / `LambdaQueryWrapper` | 全部 CRUD |
| 分页插件（`IPage`） | 服务端分页（`P01`、`J01`、`U03`） |
| `resources/mapper/PostMapper.xml` | 标签聚合等复杂 SQL（`P04`） |
| DTO / VO + `@Valid` | 出入参与校验（`P05`、`J03`、`S02`） |
| **多对多关联**（`tag` + `post_tag`） | 标签建模（`P04`） |
| `@TableLogic` | 逻辑删除（`P10`、`J04`） |
| MySQL JSON 字段 | 项目的 `tech` / `links`（`J05`，刻意不建关联表） |
| Multipart + 静态资源映射 + `StorageService` | 图片上传（`U01`～`U03`） |
| 聚合 SQL | 仪表盘统计（`T06`） |

**关键产出**

- 文章：分页列表（关键词 + 3 种排序 + 方向）、详情、新增、编辑、单删、批量删
- 标签：按名 `INSERT IGNORE` 建档 → 重建 `post_tag` → 查询时聚合成 `string[]`
- 项目：同构 CRUD（JSON 字段）
- 媒体：上传接口（校验 MIME + 5MB）、列表、删除
- 站点配置：`GET` / `PUT`
- 仪表盘：一条聚合 SQL 返回总数、各状态数、最近更新
- **前端**：`lib/cloud.ts` → `lib/api.ts`；`store.tsx` 适配分页返回结构

**完成标准**

1. 造 1 万条数据，列表接口响应 < 200 ms，`EXPLAIN` 命中 `idx_list`；
2. 前端文章 / 项目 / 媒体 / 配置 / 仪表盘全部可用，**行为与改造前一致**；
3. Controller 内无业务 `if`，全部返回 VO。

**注意**

- **前端接通宜早不宜迟**，这一步最容易暴露接口设计问题；
- 接口字段名必须与前端现有类型严格一致（`date`、`tags: string[]`、`isSample`），否则前端改动会失控。

### 阶段四 · 深度（业务逻辑与并发控制）⭐

**目标**：把「能用的 CRUD」升级为「有业务难点的系统」。**这一阶段决定面试官对你的评价。**

**覆盖需求**：`FR-B-P06`～`P09`、`P11`｜`FR-B-T01`、`T02`

**使用技术**

| 技术 | 满足的需求 | 为什么是难点 |
| --- | --- | --- |
| 枚举 + **状态机**（集中定义合法边） | 状态流转（`P07`） | 业务规则从散落 `if` 变成可校验的模型 |
| **`@Transactional`** 跨表写入 | 发布流程（`P07`、`P08`） | 一致性保证；回滚条件、传播行为都要讲清 |
| `post_revision` 快照表 | 历史版本与回滚（`P08`） | 让事务有真实内容 |
| **`@Version` 乐观锁** | 并发编辑（`P06`） | 冲突检测返回 `409`，是并发控制的入门必会 |
| `@TableLogic` + 回收站接口 | 回收站（`P11`） | 逻辑删除的完整闭环 |
| **AOP + 自定义注解 + `@Async`** | 审计日志（`T01`、`T02`） | 零侵入横切，注解一加即生效 |

**关键产出**

- `PostStatus` 枚举 + 状态机（合法流转边集中定义，非法流转抛 `STATE_ILLEGAL`）
- `PUT /api/posts/{id}/status`：发布 / 归档 / 回退为草稿
- `@Transactional` 发布流程：更新 `post` + 插入 `post_revision`，任一失败整体回滚
- `GET /api/posts/{id}/revisions` + 回滚接口（回滚本身也是一次事务）
- 乐观锁冲突 → `409 VERSION_CONFLICT`
- 回收站：列表 + 恢复
- `@OperationLog` 注解 + `OperationLogAspect`（`@Around` 记耗时、操作人、IP，`@Async` 落库）
- 前端：状态切换、编辑冲突提示、回收站页面

**完成标准**（每条都必须能现场演示）

1. 两个会话并发编辑同一文章 → 后提交者收到 `409`，且**内容未被覆盖**；
2. 在发布流程中人为抛异常 → `post` 状态未变、`post_revision` 无新增（**事务回滚**）；
3. 删除后列表不可见、回收站可见、恢复成功，DB 中 `deleted = 1`；
4. 每次发布在 `operation_log` 留下记录（含操作人、耗时、IP）。

**注意**

- `@Transactional` 基于代理，**同类内部自调用不生效**；默认只回滚 `RuntimeException`，受检异常需显式声明；
- 逻辑删除与唯一索引的冲突见架构文档 §5.1「已知取舍」。

### 阶段五 · 完备（剩余模块与缓存）

**目标**：补齐剩余功能，并给项目加上「**性能**」这一维度。

**覆盖需求**：`FR-B-P12`｜`FR-B-U04`｜`FR-B-S03`｜`FR-B-T03`、`T04`

**使用技术**

| 技术 | 满足的需求 |
| --- | --- |
| `StorageService` 接口 + 本地实现 | 存储抽象，留 OSS 扩展点（`U04`） |
| Spring Cache（`@Cacheable` / `@CacheEvict`） | 文章详情与列表缓存、写时失效（`S03`） |
| Redis `INCR` + 定时任务 | 浏览量自增与落库（`P12`） |
| JSON 导入导出 + 事务 | 数据备份与恢复（`T03`、`T04`） |

**关键产出**

- 媒体存储抽象 `StorageService`（本地磁盘实现）
- 站点配置保存后清缓存
- 浏览量：阅读时 Redis 自增，定时任务每 5 分钟落库
- 导出 JSON / 导入 JSON（**差异预览 + 事务写入，失败整体回滚**）
- 缓存：详情 `@Cacheable`、列表按条件缓存、写操作 `@CacheEvict`
- **删除前端 Supabase 依赖包与调用**

**完成标准**

1. 连续两次请求文章详情，第二次**不查库**（日志或 Redis key 可见）；编辑后缓存被清除；
2. 前端**全量回归**通过（复用 `ADMIN-STAGE2-REQUIREMENTS.md` §8 的验收清单）；
3. `package.json` 中不再有 `@supabase/supabase-js`。

**注意**

- 缓存**不要追求强一致**，用「TTL + 写时失效」即可（个人站点不存在强一致需求）；
- 导入必须在一个事务里，失败要能整体回滚，避免半成品数据。

### 阶段六 · 交付（测试、容器化与部署）

**目标**：让项目「可交付、可复现、可演示」，补齐工程规范的最后一块。

| GitHub Actions | CI：编译 + 测试 |
| Nginx + HTTPS | 反向代理与证书（顺带消除浏览器安全上下文限制） |
| Actuator | 健康检查（`T05`） |

**关键产出**

- Service 单测：状态机合法 / 非法流转、乐观锁冲突、事务边界
- Controller 测试：登录、`401` / `403`、参数校验失败
- 多阶段 `Dockerfile` + 完整 `docker-compose.yml`
- `.github/workflows/backend-ci.yml`
- 部署：Nginx 反代 `/api`、HTTPS、`/actuator/health`（含 DB 与 Redis 探活）
- 请求日志补 TraceId
- **README 重写**（架构图 + 选型理由 + 接口一览 + 演示账号）

**完成标准**

1. 新机器 `git clone && docker compose up -d` → 前后端全部可用；
2. CI 绿色；线上 HTTPS 地址可访问；
3. 一个不了解项目的人，5 分钟内能看懂 README 并跑起来。

**注意**

- 测试只覆盖**核心分支**，不要为覆盖率写无意义用例；
- 部署到 HTTPS 后，前面提到的「非安全上下文」浏览器限制会自然消失。

## 4. 贯穿全阶段的纪律

| # | 纪律 | 原因 |
| --- | --- | --- |
| 1 | **每个阶段结束必须做一次端到端验证**，不允许攒到最后 | 攒到最后就是「三天修不完的 bug」 |
| 2 | **接口契约以架构文档 §6 为准**，字段名不得随意改动 | 字段名一改，前端就要跟着改，改动量会失控 |
| 3 | **每个阶段当天补文档 + 规范提交**（`feat` / `fix` / `refactor` / `docs`） | 答辩时 Git 历史本身就是工程素养的证据 |
| 4 | **不引入需求文档 §2.4.2 之外的技术** | 每多一个技术，就多一个「为什么用它」的追问风险 |
| 5 | **阶段的顺序不可打乱** | 阶段四是核心，前面地基不稳会导致它做不下去 |
